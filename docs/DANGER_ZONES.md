# 이 앱에서 건드리면 위험한 부분

2026-10-12 전체 점검에서 정리한 목록. 아래를 바꿀 때는 반드시 사장님 확인을 받고, 바꾼 뒤 직접 테스트한다.

## 데이터가 사라질 수 있는 곳
- **DB 연쇄 삭제(on delete cascade)**: 고객 행을 지우면 이용권·예약(출석/서명/운동일지)·계약서 서명·양도 이력·
  매출 계획·서명 대기·반복 규칙이 전부 함께 지워진다. 이용권 행을 지우면 양도 이력이 지워진다.
  → 앱은 삭제 대신 **보관(archived_at)** 만 쓴다. 행을 실제로 지우는 코드를 다시 만들지 말 것.
- **supabase/schema.sql 재실행**: 대부분 다시 실행해도 안전하게 만들어 뒀지만, 새 SQL을 추가할 때 데이터를 바꾸는
  문장(UPDATE/DELETE)을 넣지 말 것. 일회성 데이터 변경은 주석으로 남긴다.
- **서명 이미지(Storage `signatures`)**: 이메일 백업과 [백업 받기]에는 표 데이터만 들어가고 서명 사진 파일은 안 들어간다.

## 돈·횟수가 어긋날 수 있는 곳
- **세션 차감**: `used_sessions`가 유일한 기준(완료·노쇼 차감, 수동조정, 양도로 넘긴 횟수 포함). 예약 건수로 다시 세지 말 것.
  차감은 DB 함수(set_reservation_status / delete_reservation / register_used_reservations / close_series_from /
  transfer_pass / proxy_set_reservation_status)에서만 한 번에 일어나야 한다.
- **완료 시 이용권 자동 전환**: 묶인 이용권이 소진됐으면 가장 먼저 등록한 유효 이용권으로 차감(관리자 화면·대리 화면 모두).
- **매출 기준**: 회계관리·통계분석·매출 계획 = 실제 결제(입금)액, 미수금 별도. 페이롤 = 완료 레슨 × (판매가 ÷ 총 횟수).
  입금 날짜 기록이 없어 나중에 받은 잔금은 "이용권 등록 달" 매출에 더해진다.
- **보관한 이용권**: 잔여·매출 계산에서 빠진다(복원하면 다시 포함). 보관한 고객의 결제는 매출에 그대로 남는다.

## 권한·보안
- **역할(app_metadata.role)**: 없음 = 트레이너(관리자), "member" = 회원 마이페이지, "delegate" = 대리 트레이너.
  입구 규칙은 `src/lib/supabase/middleware.ts`. 경로를 추가할 때 세 역할이 각각 어디로 가는지 확인할 것.
- **로그인 없이 열리는 곳**: `/sign/<토큰>`(고객 링크 서명), `/delegate-login`(대리 로그인 링크), `/api/cron/backup`(CRON_SECRET 확인).
  데이터는 서버가 토큰을 확인한 뒤 관리자 키로 그 한 건만 읽는다. 표를 anon에게 열지 말 것.
- **관리자 키(SUPABASE_SERVICE_ROLE_KEY)**: 서버 파일에서만 쓴다(`src/lib/supabase/admin.ts`). 브라우저 코드("use client")에서 import 금지.

## 구조
- **`src/components/PTMemberManager.tsx`(약 3,800줄)**: 거의 모든 관리자 화면이 한 파일에 있다. 한 곳을 고치면 다른 탭이
  깨질 수 있다. 나중에 탭별로 나누는 게 좋지만(위험도 중간), 한 번에 하지 말고 한 탭씩 나눠서 테스트하며 진행할 것.
- **앱 첫 로딩**: 예약 전체를 한 번에 불러온다. 수천 건을 넘으면 느려질 수 있다(지금은 수백 건).
- **휴대폰 화면 분기(640px)**: 스케줄·매출 계획은 휴대폰에서 다른 화면을 쓴다. 기능을 바꾸면 두 화면을 모두 확인할 것.
